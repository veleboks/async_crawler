# День 4 — Rate Limiting и правила вежливости

1. **RateLimiter.** Ограничивает частоту начала запросов, а не количество одновременных запросов. Интервал равен `1 / requests_per_second`; первый запрос проходит сразу, следующие ждут. При `per_domain=True` состояние и lock отдельные для каждого hostname, при `False` используется один глобальный ключ. Интерфейс: `acquire(domain: str | None, required_delay: float = 0)`. Итоговая задержка: `max(1 / requests_per_second, min_delay, crawl_delay) + random(0, jitter)`. Значение `jitter=0` по умолчанию обеспечивает предсказуемое поведение.

2. **Связь с SemaphoreManager.** SemaphoreManager ограничивает число одновременно выполняемых запросов, RateLimiter — частоту их старта. Порядок для текущей архитектуры: получить доменный и глобальный семафоры → дождаться RateLimiter → выполнить HTTP-запрос → освободить семафоры. RateLimiter применяется только к сети; HTML-парсинг начинается после освобождения сетевых ограничителей.

3. **RobotsParser.** Для обработки правил используется `urllib.robotparser.RobotFileParser`; его синхронный `read()` не используется. Текст загружается через `aiohttp`, затем передаётся в `parse(text.splitlines())`. Интерфейс: `async ensure_loaded(url)`, `can_fetch(url, user_agent) -> bool`, `get_crawl_delay(url, user_agent) -> float | None`, `get_stats()`.

4. **Кэш robots.txt.** Ключ кэша — origin: `scheme + hostname + port`, поскольку `http://example.com`, `https://example.com` и `https://example.com:8443` могут иметь разные правила. Для каждого origin нужен отдельный lock с повторной проверкой кэша после захвата, иначе несколько worker-ов могут одновременно скачать один robots.txt. Кэш живёт до закрытия crawler-а; TTL в рамках дня не реализуется.

5. **Загрузка robots.txt.** URL строится как `{origin}/robots.txt`. Нельзя загружать его через обычный `fetch_url()`, который сам проверяет robots.txt: это вызовет рекурсию. Нужен внутренний низкоуровневый запрос без robots-проверки, но с SemaphoreManager, RateLimiter и User-Agent. Robots-запрос учитывается в статистике HTTP-запросов, но не расходует `max_pages`.

6. **Политика robots.txt.** Ответ `2xx` парсится и соблюдается; `4xx` означает разрешение обхода; `5xx` или сетевая ошибка означают полный временный запрет origin; при частично некорректном файле используются правила, которые удалось распарсить. Если `can_fetch()` возвращает `False`, HTTP-запрос страницы не выполняется, URL логируется и записывается в `blocked_urls`, а не в `failed_urls`.

7. **User-Agent.** Используется один настраиваемый HTTP User-Agent, например `MyBot/1.0`, заданный для всей `ClientSession`. Для сопоставления robots.txt используется product token `MyBot`, который является частью полного заголовка. Ротация User-Agent исключается как опциональная и усложняющая корректный выбор robots-правил.

8. **Retry и backoff.** Добавляются параметры `max_retries`, `backoff_base`, `backoff_max`. Повторяются timeout, connection errors, HTTP `429` и `5xx`; обычные `4xx` не повторяются. Задержка рассчитывается как `min(backoff_max, backoff_base * 2**retry_number)`. Backoff выполняется без удержания семафора; каждая новая попытка снова проходит через RateLimiter. Поддержка `Retry-After` остаётся вне scope.

9. **Поток запроса.** Worker получает URL → `ensure_loaded(url)` при необходимости загружает robots.txt → `can_fetch(url)` проверяет доступ → `get_crawl_delay(url)` возвращает дополнительное ограничение → HTTP-попытка получает семафоры, ожидает RateLimiter и выполняет запрос с User-Agent → при успехе HTML парсится → при retryable error выполняются backoff и новая попытка → при окончательной ошибке URL попадает в `failed_urls`. Заблокированный URL расходует `max_pages`, поскольку был принят очередью, но не учитывается как выполненный HTTP-запрос.

10. **Статистика.** Отслеживаются `requests_started`, средняя фактическая задержка RateLimiter, средняя или текущая скорость запросов, количество записей robots-кэша, количество загрузок robots.txt, `blocked_urls` и число retry. Для первой версии скорость вычисляется как `requests_started / elapsed`, а средняя задержка — как общее время ожидания limiter-а, делённое на число выданных разрешений.

11. **Тестирование.** Один домен соблюдает минимальный интервал; разные домены при `per_domain=True` не задерживают друг друга; фиксированный robots-текст правильно разрешает и запрещает пути и возвращает Crawl-delay; параллельные проверки одного origin загружают robots.txt один раз; запрещённый URL не вызывает page-fetch и попадает в `blocked_urls`; fake-fetch дважды падает и затем успешно отвечает, проверяя retry. Во всех тестах `jitter=0`, реальная сеть не используется.

12. **Порядок реализации.** Сначала реализовать и протестировать RateLimiter → добавить User-Agent → сделать RobotsParser без сети → добавить асинхронную загрузку и кэш → интегрировать блокировку в crawler → добавить статистику → реализовать retry/backoff → обновить демонстрацию и интеграционный тест. Ротация User-Agent, `Retry-After`, HTTP cache headers, token bucket и фильтры URL остаются вне scope.
